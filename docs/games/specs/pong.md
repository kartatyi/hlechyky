# Понг (`pong`) — пункт 32

**Info:** `Id="pong"`, `Title="Понг"`, `Accusative="понг"`, `Group=Live`, 2/2, `TickMs=40` (25 Гц),
`Rated=true`, `Hint="Дві ракетки, м'ячик. До семи. Стрілки ↑↓ або W/S, на телефоні — тягни пальцем"`.
`SeatName`: «ліва»/«права».

## Симуляція (на сервері, у дробових одиницях)

- Поле 160 × 100 (ширина × висота), координати `double`. Ракетки: x = 4 (ліва, місце 0) і 156 (права),
  висота 18, ширина 2, швидкість ≤ 60 од/с. М'яч: радіус 1.5, стартова швидкість 60 од/с під випадковим
  кутом ±30° у бік того, хто пропустив (перший раз — випадково), +6% за кожен відбій (макс 160 од/с).
- Відбій від ракетки: кут = (відносне попадання від центру, −1..1) × 60°; від верху/низу — дзеркально.
- Гол: м'яч за x < 0 або x > 160 → очко, пауза 1 с (`serveIn` тиків), новий розіграш.
- Партія до 7. «Готуйсь» 3 с на старті. Тайм-аут раунду — нема.
- Ввід: `Input('move', { dir: -1|0|1 })` (клавіші, утримання) АБО `Input('to', { y: number })` (палець/миша:
  бажана позиція центру ракетки; сервер рухає до неї з обмеженням швидкості). Останній отриманий ввід діє
  до наступного.

## Кадр (кожен тик)

`{ t: number, bx, by, vx, vy, p: [y0, y1], s: [score0, score1], serveIn, winner }` — `t` — номер тика
(для інтерполятора). Округляти до 0.1.

## Вид

`{ scores, phase: 'ready'|'play'|'done', startIn, winner, target: 7 }` (+ останній кадр).

## Клієнт

- Канвас 16:10, малює за інтерполятором `HGames.ui.Interp` (рендер на `requestAnimationFrame`, стан на
  «зараз − 40 мс»), м'яч зі слідом, ракетки кольорами місць. Клавіші: keydown/keyup → `move`. Палець/миша
  на канвасі: `pointermove` → `to` (throttle 30/с — ліміт хаба).
- Рахунок великими цифрами по центру вгорі; «Готуйсь» відлік.

## Тести (≥ 20)

- М'яч летить прямо в ракетку по центру → відбивається горизонтально; в край ракетки → кут ≈ 60°.
- Відбій від верху/низу; швидкість росте на 6%; стеля 160.
- Гол ліворуч → очко правому; пауза; подача в бік того, хто пропустив.
- Ракетка не виходить за поле; `to` рухає не швидше 60 од/с (за 1 тик ≤ 2.4 од).
- До 7 → Finish, Журнал «понг: X 7:4 Y».
- Перф: 5000 тиків < 1 с.
- Детермінізм кутів подачі за сідом.

### Симуляція

Усе в `PongCore` і в дробових одиницях: поле 160 × 100, вісь y вниз (як у канвасі), крок `Dt = 0.04` с.
Ракетки — центри по y, х фіксовані (4 і 156), швидкість 60 од/с і для клавіш, і для пальця. М'яч — радіус
1.5, подача 60 од/с під випадковим кутом ±30°, кожен відбій від ракетки множить швидкість на 1.06 до стелі
160. Кут відбою = (зсув попадання від центру ракетки, обрізаний до −1..1) × 60°; верх і низ — дзеркало з
поверненням «наскільки заліз, настільки й відскочив».

Два місця, де реалізація точніша за буквальний текст spec:

1. **Відбій рахується по відрізку руху, а не по кінцевій точці.** На 160 од/с м'яч долає за тик 6.4
   одиниці — перевірка «чи він зараз усередині ракетки» пропускала б його наскрізь. `PongCore.Hit` шукає
   перетин площини `край ракетки + радіус` і бере точку попадання саме там (тест
   `A_fast_ball_does_not_tunnel_through_a_paddle`).
2. **Зона попадання — `висота/2 + радіус м'яча`**, а відносне попадання при цьому обрізане до −1..1: край
   ракетки віддає рівно 60°, а м'яч, що зачепив її самим боком, не провалюється у гол.

Гол — центр м'яча за `x < 0` або `x > 160`. Очко, м'яч у центр, `serveIn = 25` тиків (1 с), подача в бік
того, хто пропустив; перша подача — випадковий бік. «Готуйсь» — 75 тиків (3 с), і ракетки в цій фазі вже
слухаються, щоб було де розім'ятись. Партія до 7. Випадковість — тільки `Ctx.Rng`, часу гра не питає взагалі.

### Ввід

`Act` один на обидва наміри (приходять через `Input`, відповіді ніхто не чекає):

- `move { dir: -1|0|1 }` — клавішу тримають; діє, поки не прийде наступний `dir`;
- `to { y }` — палець або миша просять центр ракетки отут; сервер везе її туди зі своєю швидкістю
  (≤ 2.4 од за тик), тож миша не дає переваги над клавіатурою.

Кожен новий ввід скасовує попередній (`to` гасить утримання і навпаки). Обидва приймаються і як
`{ dir: 1 }`, і як голе число. Невідома дія — `ActResult.Fail("Тут так не ходять")`.

### Кадр і вид

Кадр летить щотика, повні види — лише коли змінилось те, чого в кадрі не видно (кінець «готуйсь», очко,
кінець партії).

```jsonc
// Frame()
{ "t": 78, "bx": 80.0, "by": 50.0, "vx": 59.1, "vy": -10.4,
  "p": [50.0, 62.4], "s": [3, 4], "serveIn": 0, "startIn": 0, "winner": null }
```

**Відхилення від spec:** у кадрі є ще `startIn`. Spec його там не називав, але відлік «Готуйсь 3…2…1»
міняється щотика, а види в цій фазі вже не летять — і платформа прямо каже брати реалтайм-статус із
`ctx.frame`, а не з `ctx.view` (INTEGRATION-NOTES §3). Одне мале число на кадр дешевше, ніж повний вид
75 разів поспіль.

```jsonc
// View(seat) — однаковий для обох місць і для глядача, ховати тут нема чого
{ "scores": [3, 4], "phase": "play", "startIn": 0, "winner": null, "target": 7,
  "turn": null, "frame": { … } }
```

`winner` — номер місця (`0` ліва, `1` права) або `null`; нічиїх у понзі не буває. `turn: null` — ходів тут
нема, але каркас питає це поле в кожної гри. Останній кадр вкладено у `frame`: так картка малює поле ще до
першого тика (стіл, що чекає на суперника, виглядає як поле, а не як порожнеча).

Рядок Журналу — у стилі решти платформи, з назвами місць: `Понг: Оля ліва 7:3 Петро права` (spec писав
коротше, «понг: X 7:4 Y», але сусідні ігри пишуть саме так, і чіпи місць у картці підписані тими ж словами).

### Клієнт

- Канвас 320 × 200 (16:10), одиниця поля = 2 пікселі. Малюється не «кожен кадр як прийшов», а через
  `HGames.ui.Interp` на `requestAnimationFrame`: стан беремо на «зараз − один інтервал» і змішуємо два
  останні кадри. На голі (рахунок у сусідніх кадрах різний) інтерполяцію вимикаємо — вести м'яч через усе
  поле назад у центр було б брехнею.
- М'яч тягне слід із 10 позицій (лише поки летить), ракетки — кольорами місць (`--accent` ліва,
  `--ok` права), рахунок великими цифрами по центру вгорі, «Готуйсь» і «Виграв X» — затемненням поверх поля.
- Клавіші: `onKey` ловить `keydown`, свій слухач на документі — `keyup` (каркас `keyup` не роздає). Шлемо
  **лише зміну** напрямку, а не кожне натискання: автоповтор клавіші інакше з'їв би квоту хаба. Пішли з
  вкладки із затиснутою клавішею — `blur` спиняє ракетку.
- Палець і миша: `pointermove`/`pointerdown` на канвасі кладуть бажану позицію в стан, а відправляє її
  rAF-цикл не частіше ніж раз на 40 мс (25/с, із запасом до хабової стелі в 30). Остання позиція не
  губиться — вона просто чекає наступного вікна.
- `.pongboard.play { touch-action: none }` вішається лише тому, хто грає: глядач гортає сторінку пальцем як
  завжди.
- Хрестовина каркаса (`ui.dpad`) тут не годиться — вона на клік, а ракетку треба **тримати**. Тому свої дві
  кнопки `↑`/`↓` на `pointerdown`/`pointerup`, видимі лише при `pointer: coarse`.

### Обмеження, які лишились свідомо

- **Пропущені тики не надолужуються** — так влаштований `TickEngine` (заснув сервер — м'яч не телепортується).
- **Лаг гравця сервер не компенсує**: правда одна, вона на сервері, клієнт лише малює її з відставанням на
  один інтервал. Для понга на локальній мережі цього досить.
- **Ракетка не «підкручує» м'яч власним рухом** — кут задає лише точка попадання, як і сказано в spec.
- Коротка партія (< 20 с) черепків не приносить: у реалтайму `Moves == 0`, і економіка дивиться лише на час
  (INTEGRATION-NOTES §5). Це не баг понга.
